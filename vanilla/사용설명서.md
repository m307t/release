# 법제업무팀 사용설명서

법제업무 에이전트 팀을 설치하고, 일을 맡기고, 결과를 검수하는 방법을 정리한 설명서입니다.

> **목적과 최종 책임**
>
> 이 에이전트 팀은 법제업무, 검토보고서 작성 업무, 예결산 검토 업무를 보조하고 그를 위한 일정관리와 자료조사를 하는 도구입니다. 법률 자문이나 기관의 공식 의견을 대신하지 않습니다.
>
> 사용자와 함께 시행착오를 겪으며 성장하도록 설계했기 때문에, 배포 시점에는 미숙할 수 있습니다. 처음 쓰는 동안에는 결과물을 더 꼼꼼히 검수하고, 찾은 오류와 맞지 않는 곳을 알려 주세요.
>
> 결과물은 모두 초안입니다. 사람이 밖으로 내거나 최종 문서로 쓰는 것은 최종 검수자가 원문과 대조해 승인한 것뿐이고, 내용과 쓰임에 대한 판단과 책임은 승인한 사람과 그 소속 기관에 있습니다. 팀 사이에 넘기는 중간 결과물(조사노트 등)은 넘겨받은 팀의 승인 관문에서 다시 검수합니다. 검증 에이전트의 '통과'는 사람 검수를 대신하지 않습니다. 전체 문구는 [면책고지.md](면책고지.md)에 있습니다.

처음이라면 [튜토리얼.md](튜토리얼.md)로 한 건을 끝까지 돌려 본 뒤, 필요한 곳을 이 설명서에서 찾아 읽기를 권합니다. 짧은 소개와 구성 표는 [README.md](README.md)에 있습니다. 규칙의 원본은 언제나 `CLAUDE.md`와 각 팀장 스킬이며, 이 설명서는 그 내용을 사람이 읽기 쉽게 풀어 쓴 것입니다.

### 팀장·실무·검증
팀마다 세 역할이 있습니다. 팀장이 일을 나누고, 실무가 쓰고, 검증이 따로 봅니다.

| 역할 | 파일 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| 팀장 | `.claude/skills/<팀ID>/SKILL.md` | 건 폴더를 만들고, 사람에게 묻고, 실무·검증을 부르고, 기록합니다 | 사람 확인 없이 방향·결론을 정하지 않습니다 |
| 실무 | `.claude/agents/<팀ID>-writer.md` | 위임지시대로 초안을 씁니다 | 원자료를 고치지 않고, 확인하지 못한 것을 추측으로 채우지 않습니다(`[확인 필요]`) |
| 검증 | `.claude/agents/<팀ID>-checker.md` | 결과물과 원자료만 받아 통과·보완·반려를 판정합니다 | 파일을 고치지 않습니다. 실무의 메모나 팀장의 기대 결론을 받지 않습니다 |

- 법안검토팀은 검토보고서 플러그인(`bill-review@ai-assembly`)이 실무 엔진입니다. 이 팀의 실무·검증 에이전트는 플러그인이 없을 때 쓰는 예비입니다.
- 상황실은 뉴스 모드 전용 실무·검증(`ops-desk-news-writer`, `ops-desk-news-checker`)이 따로 있습니다.
- 대비표를 만드는 팀(법제팀, 심사지원팀 소위자료, 법안검토팀 예비 경로)은 검증 전에 조문 대조 검사기를 돌립니다. 같은 모델이 쓰고 같은 모델이 보면 같은 착각을 하므로, 글자 대조는 코드로 합니다.

### 한 건이 지나가는 길

```text
1  안내실       입력 파일을 넣고 평소 말로 요청
2  회의실       팀 배정, 건 폴더 이름을 한 줄로 알림
3  팀장         건 폴더와 _진행.md, [사람 확인] 방향·범위, 위임지시
4  실무         01_ 초안
5  조문 대조    대비표를 만드는 팀만: 검사기로 원장과 글자 대조 (불통과면 실무로 되돌림)
6  검증         통과 / 보완(실무로 되돌림) / 반려(사람에게)
7  검수포인트   03_검수포인트.md: 사람이 먼저 볼 곳
8  사람 승인    직접 고친 곳 확인, 승인한 것만 04_최종_
9  오류노트     라운지 오류노트에 익명으로 한 줄
10 역량강화실   오류노트 → 검수 체크리스트 → 다음 건의 검증 기준
```

어느 단계에서든 사람의 판단이 필요하면 팀장이 멈추고 묻습니다. 검증을 통과해도 사람이 승인하기 전에는 최종본이라 부르지 않습니다. 사람이 찾아낸 오류는 오류노트를 거쳐 체크리스트가 되고, 다음 건부터 검증이 그 항목을 봅니다.

| Node.js 20 이상 | kordoc | 없으면 설치키트가 설치합니다(Windows는 winget, macOS는 Homebrew). Linux는 직접 설치합니다 |
| 인터넷 | kordoc 내려받기(npm), 법령 MCP, 웹 조사 | 클라우드 세션은 환경의 네트워크 설정을 따릅니다 |

Python 3.8 이상이 없으면 상황실의 파일 메일·캘린더 처리, 조문 대조, 예결산 검증, 대시보드를 할 수 없습니다.

### 내 비공개 저장소 만들기
배포본(`vanilla`)은 아무 기록이 없는 빈 사무실입니다. 쓰는 기관이 자기 GitHub 계정에 **비공개(Private) 저장소**를 새로 만들어 옮겨 담습니다. 일을 할수록 선례·오류노트·체크리스트·통합일정표가 쌓이므로 Public 저장소로 쓰지 않습니다.

1. GitHub에서 새 저장소를 **Private**으로 만듭니다. README·.gitignore·라이선스를 더하지 않은 빈 저장소로 만듭니다.
2. 배포 저장소에서 받은 `vanilla` 폴더 안의 파일을 PC의 새 폴더(예: `법제업무팀`)에 그대로 복사합니다. 이름이 점(.)으로 시작하는 숨김 항목(`.claude` 폴더, `.gitignore`, `.gitattributes`)도 빠짐없이 복사합니다. 배포 저장소 안의 `vanilla` 폴더에서 바로 Claude를 열거나 동기화를 돌리지 않습니다(동기화 스크립트는 저장소 맨 위가 아니면 멈춥니다).
3. Git 사용자를 등록합니다(PC마다 한 번).
   ```bash
   git config --global user.name "이름"
   git config --global user.email "메일주소"
   git config --global core.quotepath false   # show Korean file names as-is
   ```
4. 그 폴더에서 저장소를 만들고 1의 GitHub 저장소를 연결합니다.
   ```bash
   cd 법제업무팀
   git init -b main
   git remote add origin https://github.com/<계정>/<저장소>.git
   ```
5. 첫 동기화로 올립니다. macOS·Linux는 `./동기화.sh`, Windows는 `동기화.cmd`를 더블클릭합니다. 올릴 파일 목록을 먼저 보여 주고, `y`를 눌러야 올립니다.

다른 PC에서는 저장소를 받아서 씁니다. 비공개 저장소라 GitHub 로그인 창이 뜨면 저장소에 접근할 수 있는 계정으로 로그인합니다.

```bash
git clone https://github.com/<계정>/<저장소>.git 법제업무팀
```

### 도구 설치 (PC마다 한 번)
| OS | 실행 |
|---|---|
| Windows | `도구\설치키트\install-windows.bat` 더블클릭 |
| macOS·Linux | 터미널에서 `bash 도구/설치키트/install.sh` |

| 설치되는 것 | 하는 일 | 비고 |
|---|---|---|
| kordoc (CLI + MCP) | HWP·HWPX·PDF 읽기, HWPX 만들기 | 인터넷(npm)에서 받습니다. Claude Code(사용자 범위)와 Claude Desktop에 자동 등록됩니다 |
| 검토보고서 플러그인 `bill-review@ai-assembly` | 법안검토팀의 실무 엔진 | Claude Code가 있을 때만 등록됩니다. Claude Code를 나중에 설치했으면 설치키트를 다시 실행합니다(같은 판을 다시 복사·등록합니다) |
| Node.js 20 이상 | kordoc 실행 | 없을 때만 설치합니다 |
| KISA 범피스 (Windows, 선택) | — | **배포본에 들어 있지 않습니다.** 아래를 봅니다 |

- KISA 범피스는 제3자 프로그램이라 배포본에 넣지 않았습니다([제3자고지.md](제3자고지.md)). Windows 설치의 4단계는 `도구/설치키트/payload/windows/`에 .exe가 없으면 그 단계만 건너뜁니다.
- 이 프로그램이 필요하면, 어디서 받아 쓸지는 쓰는 사람과 기관이 정합니다. 받은 .exe를 그 폴더에 넣고 설치키트를 다시 실행하면 복사와 바로가기 만들기를 합니다(설치 스크립트는 이 프로그램을 실행하지 않습니다).
- 넣은 .exe는 `.gitignore`(`도구/설치키트/payload/windows/*.exe`)가 이미 동기화에서 빼므로 PC마다 넣습니다. 넣기 전에 그 파일의 재배포 조건을 확인합니다. macOS·Linux에는 설치하지 않습니다.

설치가 끝나면 Claude 앱(Claude Code·Claude Desktop)을 다시 시작하고 확인합니다. 자동 등록이 실패했으면 `도구/설치키트/README.md`의 '수동 등록'을 따릅니다.

```bash
kordoc --version          # the version written in 도구/설치키트/README.md
claude mcp list           # kordoc ... Connected
claude plugin list        # bill-review@ai-assembly enabled
```

클라우드 세션(claude.ai/code)에는 kordoc과 검토보고서 플러그인이 없습니다. 그래서 법안검토팀은 설치키트를 실행한 PC에서 이어 할지 묻고, HWP 입력은 PDF로 바꿔 넣어야 합니다.

| Google Calendar 커넥터 | claude.ai 설정 → 커넥터. 공유하지 않는 전용 캘린더를 Google Calendar에서 미리 만들어 두고 이름을 알려 줍니다 | `.ics` 파일을 만들어 드리면 Google Calendar 설정 → 가져오기로 넣습니다 |
| 문서 스킬 `bill-hwpx-autofill`, `amendment-comparison-table`, `참고조문`, `legislative-review` | 배포본에 들어 있지 않고 공개된 표준 스킬도 아닙니다. 기관이 따로 마련해 claude.ai 계정 스킬로 둔 경우에만 씁니다 | 발의서 HWPX, 대비표·참고조문 DOCX를 만들지 않고 마크다운으로 남긴 뒤 "도구 미연결로 ○○ 파일 미생성"이라고 알립니다. `legislative-review`가 없으면 법제 검증은 법제팀 팀 설정의 검토 기준으로만 봅니다 |
| 문서 스킬 `xlsx`, `docx`, `pdf` | claude.ai 계정 스킬. 계정에 있으면 씁니다 | 예결산 재계산 XLSX(`xlsx`), 필요할 때의 DOCX(`docx`), kordoc이 없을 때의 PDF 읽기(`pdf`)를 하지 못합니다. 만들지 못한 파일은 위와 같이 알립니다 |
| 열린국회정보 API 인증키 | 저장소 맨 위 `.env`에 `ASSEMBLY_KEY=…` 한 줄을 넣고 `python3 도구/국회API점검.py`로 확인합니다 | 키가 없어도 한 번에 5건까지는 조회됩니다 |

- `.env`는 동기화되지 않으므로 PC마다 만듭니다. 메모장에서는 인코딩을 UTF-8로 골라 저장합니다.
- 인증키 값은 채팅창에 붙여 넣지 않습니다. 점검 도구도 키 값을 출력하지 않습니다.

### 국가법령정보 MCP 연결
법령은 기억이 아니라 원문으로 확인하는 것이 이 팀의 원칙이라, 법령 MCP 연결을 권합니다. 이 MCP 서버는 배포본에 들어 있지 않으므로 쓰는 사람이 직접 연결합니다. 검토보고서 플러그인 안내가 권하는 서버는 제3자 오픈소스 **korean-law-mcp**(`github.com/chrisryugj/korean-law-mcp`, MIT, 법제처 Open API 기반)입니다. 아래는 2026. 11. 5.에 그 저장소 안내로 확인한 방법이며, 바뀌었으면 그 안내를 따릅니다.

| 쓰는 곳 | 연결하는 법 |
|---|---|
| Claude Code (PC) | `/plugin marketplace add chrisryugj/korean-law-mcp` 다음 `/plugin install korean-law@korean-law-marketplace` (플러그인 `skills/bill-sources/SKILL.md` §1) |
| claude.ai·클라우드 세션 | claude.ai 설정 → 커넥터 → 커스텀 커넥터 추가. 넣을 주소는 그 저장소의 README에 있습니다 |

- 인증키: 법제처 Open API(open.law.go.kr)에서 신청하는 인증키(OC)입니다. 서버를 PC에 직접 설치해 쓰면 꼭 필요하고, 공개 서버로 연결하면 키 없이 공용 한도로도 됩니다(그 README 기준). 키는 채팅창에 붙여 넣지 않고 그 서버 안내대로 설정에 넣습니다.
- 법령 MCP 서버도 외부 서비스입니다. 에이전트는 법령명·조문 번호 같은 공개 키워드로만 조회하게 되어 있습니다(보안 수칙). 공개 서버를 쓸지 PC에 설치해 쓸지는 기관 보안 지침에 맞춰 정합니다.
- 도구 이름은 연결 방식에 따라 다르게 보입니다(예: `mcp__korean-law__get_law_text`). 에이전트는 끝 이름(`search_law`, `get_law_text`)으로 찾습니다.
- 연결한 뒤 Claude 앱을 다시 시작하고, Claude Code에서 `/mcp`로 보이는지 확인합니다.

### 첫 실행 점검
1. `법제업무팀` 폴더에서 `claude`를 실행하거나, 데스크톱 앱에서 이 폴더를 엽니다.
2. "구성 점검해 줘"라고 요청합니다. Claude가 `python3 도구/구성점검.py`를 돌립니다. 마지막 줄이 `결과: 오류 0건`이면 준비가 끝난 것입니다.
   ```text
   구성 점검: 팀 8개, 에이전트 18개
   결과: 오류 0건, 주의 0건
   ```
3. 조문 대조 검사기 자체검사를 한 번 돌립니다. 조문 대조는 플러그인을 설치하지 않은 PC에서도 이 경로의 검사기로 합니다.
   ```bash
   python3 도구/설치키트/payload/AI-Assembly/plugins/bill-review/skills/article-check/scripts/article_check.py --selftest
   ```
4. (선택) 열린국회정보 API를 쓰면 `python3 도구/국회API점검.py`로 접속과 키를 확인합니다.
5. (선택) 대시보드를 한 번 만들어 열어 봅니다([대시보드](#대시보드)).

## 요청하는 법

### 평소 말로
명령어 없이 평소 말로 요청해도 회의실이 알맞은 팀에 배정합니다. 배정하면 한 줄로 알립니다.

```text
배정: 법안검토팀 / 건 폴더: 산출물/20261026_법안검토_○○법_XXXXXXX/
```

| 이렇게 말하면 | 가는 곳 |
|---|---|
| "안내실에 넣은 의뢰서로 법제 시작해 줘", "일부개정안 초안 만들어 줘" | 법제팀 |
| "이 법률안 검토해줘", "검토보고서", "쟁점 정리" | 법안검토팀 |
| "예산 검토", "결산 검토", "집행률 봐 줘" | 예결산팀 |
| "해외 입법례 찾아 줘", "통계 찾아 줘", "판례 조사" | 조사팀 |
| "자료요구서 만들어 줘", "소위자료", "축조심사" | 심사지원팀 |
| "12월호 뉴스레터", "소식지" | 뉴스레터팀 |
| "오늘 일정", "메일 정리", "이번 주 할 일", "캘린더 동기화", "아침 뉴스", "현안 소식" | 상황실 |
| "검수 포인트", "선례 대조", "체크리스트 갱신", "훈련", "채점" | 역량강화실 |
| "구성 점검해 줘", "대시보드 갱신해 줘", "동기화해 줘" | 회의실이 직접 |

- 사실 확인 한 줄이면 팀을 부르지 않고 바로 답합니다.
- 팀이 둘 이상 필요하면 선행 팀부터 부릅니다. 예: 조사팀 → 법안검토팀 → 심사지원팀.
- 검토보고서는 플러그인 스킬을 직접 부르지 않고 법안검토팀(`/bill-review`)으로 시작합니다. 플러그인은 팀장이 부릅니다.
- 업무 요청은 이 저장소의 팀장 스킬이 계정의 범용 스킬(`deep-research`, `docs`, `morning` 등)보다 먼저입니다. 계정 스킬을 이름으로 직접 지정하면 따르되, 건 내용이 들어가면 게시 범위에 걸리는지 먼저 알려 줍니다.

### 이어서 하기
건은 하루에 끝나지 않는 경우가 많습니다. 이어 하려면 "○○법 건 이어서 해 줘"라고 요청합니다. 팀장이 그 건 폴더의 `_진행.md`부터 읽고 '다음 할 일'에서 다시 시작합니다.

```text
# 진행기록
- 건: 20261105_법제_○○법
- 익명 ID: 건-XXXXXX
- 팀: 법제팀
- 접수일: 2026. 11. 5.
- 대상: ○○법 · 발의 전 · ○○○ 의원실
- 넘겨받은 자료: 없음
- 마감: S-20261105-1A2B
- 현재 단계: 3 1차 입안 방향
- 다음 할 일: [사람 확인] 1차 입안 방향: 입안 방식과 정책 선택지 고르기
```

- `_진행.md`에는 사람 결정, 검증 회차, 승인이 표로 쌓입니다. 형식은 `자료실/서식/진행기록.md`입니다.
- 같은 이름의 건 폴더가 이미 있으면 Claude가 그 `_진행.md`를 보여 주고 같은 건인지 묻습니다. 같은 건이면 이어 하고, 다른 건일 때만 이름 끝에 `_2`를 붙입니다.
- 건 폴더(`산출물/`)는 동기화되지 않습니다. 같은 PC에서 이어 하고, 다른 PC에서 이어 하려면 건 폴더를 통째로 옮깁니다.

### 사람 확인 — 사람이 정하는 곳
판단이 필요한 지점에서 팀장은 멈추고, 선택지 2~4개와 각 선택지의 근거·영향을 짧게 보여 준 뒤 답을 기다립니다. 그동안 `_진행.md`의 '다음 할 일'은 `[사람 확인]`으로 시작합니다. 상황실 브리핑과 대시보드는 이 표시로 기다리는 건을 모읍니다.

```text
[사람 확인] 1차 입안 방향 — ○○법 일부개정 의뢰 (가상 예시)
1. 신고제 유지 + 사후 점검 조항 신설
   근거: 의뢰서 R1·R2 / 영향: 개정 조문 2개, 부칙 경과조치 필요
2. 허가제로 전환
   근거: 의뢰서 R2 / 영향: 기존 사업자 경과조치, △△법 인용 조문 정비 필요
3. 의뢰자에게 R2의 뜻을 다시 확인한 뒤 정하기
덧붙여: 의뢰 범위 밖의 자구·인용 정비를 함께 할까요?
```

- 번호나 짧은 말로 답하면 됩니다. 예: "1번으로. 자구 정비는 하지 않음."
- 답은 `_진행.md`의 사람 결정 표에 원문 그대로, 일시와 함께 적힙니다. 조건이 있으면 한 번에 적어 주는 편이 정확합니다.
- 형식·표기·오탈자, 원문으로 확인할 수 있는 사실은 묻지 않고 넘어갑니다.
- 바로 답하지 못해도 됩니다. 건은 `[사람 확인]` 상태로 남고, 나중에 "이어서 해 줘"로 다시 시작합니다.
- 건을 그만두려면 "이 건은 여기서 중단해 주세요"라고 답합니다. 팀장이 그 답(중단)을 `_진행.md` 사람 결정 표에 원문 그대로 적고 '다음 할 일'을 `없음(종결)`으로 바꿉니다. 현안목록에 올라 있던 건이면 상태를 종료로 바꿉니다. 통합일정표의 그 건 `제안` 줄은 팀장이 지우고, `확정` 줄은 팀장이 알려 준 일정 ID대로 다음 상황실 실행 때 승인을 받아 `취소`로 바꿉니다. 그래서 상황실 브리핑과 대시보드에서 끝난 건으로 보이고, 그 건의 일정은 `취소`까지 마친 뒤에 다가오는 마감에서 모두 빠집니다.

### 검증 판정 읽기
검증 판정은 셋 중 하나입니다. 기준과 판정문 형식은 `자료실/규칙/검증공통.md`에 있습니다.

| 판정 | 뜻 | 그다음 |
|---|---|---|
| 통과 | 통과 조건을 모두 충족하고 중대 지적 0건 | 검수포인트를 만들고 사람 확인·승인으로 갑니다. 아직 최종본은 아닙니다 |
| 보완 | 중대 지적 1건 이상이거나 통과 조건 미충족, 고치면 해결됨 | 검증 지적사항만 실무에게 되돌려 고친 뒤(`01_초안_v2.md` 등) 다시 검증합니다 |
| 반려 | 방향이 틀렸거나, 원자료가 부족하거나, 사람 판단이 필요한 쟁점 | 되돌리지 않고 바로 사람에게 묻습니다 |

- 지적은 중대(사실·법적 효과가 틀리거나 의뢰 취지가 빠짐), 보통(이해를 해치거나 기관 형식에 어긋남), 경미(표기·오탈자)로 나뉩니다.
- 유형 코드는 인용·수치·누락·체계·최신·형식·논리·판단·중립·보안입니다. 오류노트도 같은 코드를 씁니다.
- 판정문은 건 폴더의 `02_검증보고.md`에 회차별로 쌓입니다. 원문으로 확인하지 못한 것은 판정문의 `[확인 필요]` 목록에 따로 적힙니다.

### 보완 한도와 회차
되돌림이 끝없이 돌지 않도록 한도가 있습니다. 회차와 한도는 따로 셉니다.

- **검증 회차**: 검증에 넘긴 차례입니다. 1부터 건이 끝날 때까지 이어 셉니다.
- **한도 셈**: 검증 보완과 조문 대조 불통과로 실무에게 되돌린 수입니다. 이 수가 운영 설정의 보완 한도를 넘게 되면 반려와 같이 사람에게 넘깁니다. 예를 들어 한도가 2회면 두 번까지 되돌리고, 그다음 보완은 사람에게 갑니다.
- 사람이나 상급자의 요구로 되돌린 것은 한도에 세지 않고 `_진행.md`에 따로 적습니다. 그 뒤의 셈은 0부터 다시 시작합니다.
- 법안검토팀의 플러그인 경로는 이 한도 대신 플러그인의 고정 횟수(관문 수정 1회, 조문 대조 검문소 재실행 최대 2회)를 따르고, 넘으면 보류하고 사람에게 묻습니다. 운영 설정의 보완 한도는 법안검토팀 예비 경로와 다른 팀에 적용됩니다. 그래서 보완 한도를 바꿔도 플러그인 경로의 횟수는 바뀌지 않습니다.

### 승인과 "직접 고친 곳"
검증을 통과하면 팀장이 `03_검수포인트.md`에 사람이 먼저 볼 곳을 운영 설정의 검수포인트 개수만큼 고릅니다. 이 파일의 맨 끝에는 늘 이 한 줄이 있습니다.

```text
이 초안은 AI 에이전트가 작성했습니다. 원문 대조와 최종 판단은 최종 검수자가 합니다.
```

- 상급자 피드백이나 `/coaching 포인트`로 이 파일을 고치거나 덧붙일 때도 이 줄은 맨 끝에 한 번만 둡니다.
- 이 줄과 상급자 피드백 때 더하는 '피드백 반영' 소절은 검수포인트 개수에 세지 않습니다.

1. 검수포인트부터 보고, 결과물을 원문과 대조합니다.
2. 고칠 것이 있으면 말로 요구합니다. 요구는 `_진행.md`에 원문으로 적히고 위임지시의 '사람이 정한 것'에 더해져, 실무 보완 → 조문 대조(대비표 팀) → 검증을 다시 거칩니다.
3. 승인할 때는 "승인"이라고 말합니다. 법제팀은 "확정"이라고 말해야 발의서 출력으로 갑니다.
4. 승인할 때 Claude가 "검수 중 직접 고친 곳이 있었나요?"라고 묻습니다. 파일을 직접 고쳤으면 어디를 고쳤는지 알려 줍니다.
5. 사람이 승인한 것만 `04_최종_*` 이름으로 저장됩니다.

- 직접 고친 곳은 `_진행.md` 승인 칸에 적히고, 오류노트에 '발견자: 사람'으로 올라갑니다. 사람만 찾은 오류는 가장 값진 교본 재료입니다.
- 대조 대상 파일(대비표 등)을 직접 고쳤으면, 출력이나 최종본 저장 전에 고친 파일로 조문 대조를 다시 돌려 통과를 확인합니다.

## 팀별 사용법

각 팀의 진행 단계는 팀장 스킬의 '절차'를 요약한 것입니다. 사람이 정하는 지점은 **[사람 확인]**으로 표시했습니다. 건 폴더·`_진행.md`·현안 등록·검증·오류노트는 모든 팀이 같은 규칙(`CLAUDE.md`)을 따릅니다.

분량·건수·기간 같은 숫자는 각 팀장 스킬 '팀 설정'의 배포 당시 값입니다. 바꾼 뒤의 값은 그 팀 설정에서 확인합니다.

### 법제팀 `/lawdraft`
- **언제**: 법률안 입안 의뢰서를 받아 개정문·부칙·대비표와 발의서를 만들 때. "법제 시작", "의뢰서 입안", "조문 만들어 줘", "일부개정안 초안".
- **넣을 것**: 의뢰서(HWP·HWPX·PDF 등)를 `안내실/`에 넣거나 `/lawdraft <의뢰서 경로>`로 줍니다.

1. 접수: 건 폴더(팀 이름 `법제`)를 만들고 의뢰서를 `원자료/`로 옮깁니다. 회신 기한이 있으면 마감을 역산해 통합일정표에 `제안` 줄로 넣습니다.
2. 의뢰 분석(팀장): 요구사항을 R1, R2…로 나누고 현행 조문을 법령 MCP 원문으로 확인합니다(시행예정 개정 포함). 결과는 `01_의뢰분석.md`, 조회 응답은 `원장/`에 둡니다.
3. **[사람 확인] 1차 입안 방향**: 입안 방식(일부개정·전부개정·제정)과 정책 선택지 2~4개 중에서 고릅니다. 의뢰 범위 밖 정비(자구·인용 정비)를 함께 할지도 답합니다.
4. 위임: 실무(`lawdraft-writer`)가 초안을 씁니다.
5. 조문 대조: `01_초안.md`와 `01_대비표.md`를 하나씩 원장과 글자 대조합니다.
6. 검증: 「법제기준과 실제」(국회 법제실) 기준, 요구사항 반영, 인용 조문·시행예정 개정, 부칙, 타법 영향을 봅니다.
7. 검수포인트를 만듭니다.
8. **[사람 확인] 2차 확정**: 최종 검수자가 "확정"이라고 말한 뒤에만 출력합니다.
9. 출력: `bill-hwpx-autofill` 스킬로 발의서 HWPX를 만듭니다. 대비표 DOCX는 `amendment-comparison-table`, 참고조문 DOCX는 `참고조문` 스킬로 만듭니다. 스킬이 없으면 마크다운 확정본만 `04_최종_발의서.md`로 저장합니다.
10. 기록: 오류노트에 적고, 현안목록의 상태를 종료로 바꿉니다.

| 결과물 | 내용 |
|---|---|
| `01_의뢰분석.md` | 요구사항, 해당 현행 조문, 입안 방식 후보, 타법 영향 후보 |
| `01_초안.md` | 개정문·부칙(시행일·경과조치·적용례), 끝에 타법 영향 목록 |
| `01_대비표.md`, `01_참고조문.md`, `01_요구사항매핑.md` | 현행·개정안 2단 대비표, 인용 조문 원문, 요구사항 → 반영 조문 |
| `04_최종_발의서.hwpx` | 확정 뒤 출력 |

- **먼저 볼 곳**: 정책 판단이 들어간 조문, 부칙 경과조치, 타법 영향, `[확인 필요]` 표시.
- **주의**: 입안 방향을 정하기 전에는 조문을 쓰지 않고, 확정 전에는 HWPX를 만들지 않습니다. 정책 선택이 남은 곳은 초안에 `[판단 필요]`로 남습니다.

### 법안검토팀 `/bill-review`
- **언제**: 법률안의 위원회 검토보고서 초안을 만들 때. "검토보고서", "법안 검토", "이 법률안 검토해줘", "쟁점 정리".
- **넣을 것**: 법률안 원문(PDF·HWP)을 `안내실/`에 넣거나 의안번호를 줍니다. 의안번호만 주면 플러그인이 공개 자료원에서 원문을 받아 보고, 받지 못하면 원문을 붙여 달라고 합니다. 상정 예정일을 알면 함께 알려 줍니다. 조사팀이 먼저 조사했으면 그 조사노트가 '넘겨받은 자료'로 이어집니다.

1. 접수: 건 폴더(팀 이름 `법안검토`)를 만들고 원문과 `.md` 사본을 `원자료/`에 둡니다.
2. 의안 정보·기한: 의안번호·제안자·제안일·회부일·소관 위원회를 원문에서 확인합니다. 상정 예정일이 있으면 배부 기한을 역산해 통합일정표에 `제안` 줄로 넣습니다. **[사람 확인]** 병합 대상 법률안이 있는지 답합니다.
3. 엔진 확인: 검토보고서 플러그인이 보이면 플러그인 경로로 갑니다. 보이지 않으면 **[사람 확인]** 고릅니다 — 설치키트를 실행한 PC에서 이어서 한다(권장) / 이 세션에서 예비 경로로 진행한다.
4. 플러그인 경로: 검토설계 → 관문①(설계 판정) → **[사람 확인] 쟁점 승인** → 자료조사·조문 원장 → 집필 → 조문 대조 검문소 → 관문②(초안 검수) → 한글(.hwpx) 변환 → 최종 보고 순으로 진행합니다.
   - 되돌림 횟수는 플러그인이 정합니다. 관문①·②의 수정은 1회, 검문소 재실행은 최대 2회이고, 그래도 남으면 보류하고 사람에게 묻습니다. 운영 설정의 보완 한도는 이 경로에 걸리지 않습니다.
   - 법령 MCP가 연결되지 않았으면 조문 원장을 만들 수 없어 검문소를 보류합니다.
   - 쟁점 승인에서는 쟁점 표와 함께 쟁점별 수위(원안 타당 / 수정 필요 / 신중 검토)를 고릅니다. 쟁점을 더하거나 빼거나 순서를 바꿀 수 있고, 그대로면 "승인"이라고 답합니다.
   - 검수 체크리스트가 있으면 팀장이 `사용` 항목을 `내_검토기준.md`로 옮겨 넘기고, 관문②가 항목마다 지킴·어김을 판정합니다.
5. 예비 경로: 쟁점 후보(`01_쟁점목록.md`) → **[사람 확인] 쟁점별 수위**와 협의 경과(부처 의견 등)를 넣을지 → 실무(`bill-review-writer`) → 조문 대조 → 검증(`bill-review-checker`). 입법례·통계가 필요하면 조사팀을 먼저 부릅니다.
6. 검수포인트를 만듭니다.
7. **[사람 확인] 결론과 승인**: 결론의 수위는 사람이 정합니다. 승인하면 `04_최종_검토보고서.md`(변환했으면 `.hwpx`도)로 저장합니다.
8. 기록: 오류노트에 적고 현안목록의 상태를 종료로 바꿉니다.

| 경로 | 결과물 |
|---|---|
| 플러그인 | 건 폴더 안 `_workspace/`: `00_요청.md`, `01_검토설계.md`, `02_설계판정.md`, `03_근거장부.md`, `03b_조문원장/`, `04_검토보고서.md`, `04c_조문대조.md`, `05_검수판정.md`, `06_검토보고서.hwpx` |
| 예비 | `01_쟁점목록.md`, `01_초안.md`, `01_조문검토매핑.md`, 병합 건이면 `01_대비표_<의안번호>.md`, `01c_조문대조.md`, `02_검증보고.md` |

### 조사팀 `/research`

   - 단독 건: 새 건 폴더(팀 이름 `조사`)를 만듭니다.
   - 선행 조사: 부른 건 폴더의 `조사/` 안에서 하고, 기록은 그 건의 `_진행.md`에 '조사' 단계로 남습니다.
2. 질문 쪼개기: 주제를 조사 질문 3~5개로 나눕니다(예: Q1 현행 제도, Q2 운영 통계, Q3 해외 입법례, Q4 판례·결정례, Q5 학계 견해).
3. **[사람 확인] 범위·용도**: 질문 목록, 대상 국가·기간, 결과를 쓸 팀을 확인합니다.
4. 공개 검색어 목록: 의뢰 내용·의원실 정보를 뺀 일반 키워드로 검색어를 정합니다.
5. 위임: 실무(`research-writer`)가 법령·판례(MCP) → 국회·정부 원문 → 통계 → 학술 → 언론 순으로 조사합니다.
6. 교차검증: 검증(`research-checker`)이 출처 URL을 모두 열어 인용과 대조합니다.
7. **[사람 확인] 어긋나는 자료**: 출처끼리 수치·내용이 다르면 어느 것을 채택할지 정합니다. 원문으로 확인하지 못한 것은 '전문가 네트워크 문의 목록'으로 따로 정리됩니다.
8. 단독 건 마무리: 다른 팀에 넘기지 않는 단독 건이면 조사노트 맨 끝에 AI 작성 고지 줄이 붙습니다. 밖으로 내거나 최종 문서로 쓰려면 승인을 요청해 `04_최종_조사노트.md`로 저장합니다.
9. 인계: 교차검증을 통과한 조사노트의 마지막 버전과 `출처사본/` 경로를 다음 팀에 넘깁니다. 조사노트는 팀 사이의 중간 결과물이라, 넘겨받은 팀의 승인 관문에서 다시 검수합니다.

- **결과물**: `01_조사노트.md`(질문별 답 → 근거 `[A-1]` → 어긋나는 자료, 출처표, `[확인 필요]` 목록), `출처사본/`, `02_검증보고.md`.

3. 점검: `python3 도구/일정내보내기.py 점검`으로 통합일정표를 점검해 결과를 실무에게 넘깁니다.
4. 실무가 메일을 [즉시]·[회신]·[접수]·[참고]로 나누고 브리핑·갱신안·회신 초안을 씁니다. 검증이 메일 수와 요약표 행 수, 날짜·요일·역산, 근거 없는 약속을 봅니다.
5. **[사람 확인]** 받아들일·거절할 일정과 우선순위, 회신할 메일과 명의, `제안` → `확정`으로 바꿀 줄, 캘린더에 넣을·고칠·지울 일정, 캘린더에서 바뀐 일정의 처리, 상급자 의견 메일을 피드백 절차로 넘길지를 정합니다. 넣을 캘린더가 아직 정해지지 않았으면 그 이름과, 건 칸·캘린더 제목에 이름이 들어가는 기본 형식을 그대로 쓸지도 답합니다(답하면 상황실 팀 설정과 변경이력이 고쳐지고, 형식을 바꾸면 조직 변경으로 갑니다).
6. 반영: 승인된 줄만 통합일정표에 고치고, 확정 일정을 캘린더에 옮깁니다. 대체 줄이 승인되면 그 건 `_진행.md`의 마감 칸에도 새 일정 ID를 더합니다. 승인된 회신은 `발송실/회신_YYYYMMDD_HHMM.md`로 옮기고 보내기는 사람이 합니다. 반영을 마친 메일 원본은 `안내실/처리한메일/YYYYMMDD/`로 옮겨집니다.

브리핑 한 장의 순서는 이렇습니다.
1. 오늘 마감·회의(시각순)
2. [즉시] 메일
3. [회신] 메일 — 회신 초안 있음
4. [접수] — 팀 배정 제안
5. 다가오는 마감(팀 설정의 '다가오는 마감 표시' 기간, 역산 기준 포함)
6. 사람 확인을 기다리는 건
7. 일정 — 통합일정표 갱신안, 확정할 줄, 캘린더 반영 목록
8. 오늘의 뉴스 — 같은 날 뉴스 브리핑이 있으면 한눈에 줄과 `[건 영향]` 줄

**뉴스**
1. 범위: 한국 시각 기준 직전 24시간입니다. 같은 날 브리핑이 이미 있으면 **[사람 확인]** 고릅니다 — 처음부터 다시 / 그 뒤 소식만.
2. 현안 준비(팀장): `상황실/현안목록.md`에서 진행 건과 종료 후 14일이 지나지 않은 건을 고르고, 기간이 지난 종료 줄은 지웁니다. 이 PC의 건 폴더 중 목록에 없는 건이 있으면 공개 키워드 후보를 만들어 **[사람 확인]** 승인을 받고 등록합니다.
3. 실무(`ops-desk-news-writer`)가 분야(정치·국회, 경제·금융, 사회, 국제, 산업·과학기술)별 2~3건, 심층 주제 2~3건, 현안 소식, 오늘의 일정을 모읍니다. 실무는 현안을 공개 키워드로만 압니다.
4. 검증(`ops-desk-news-checker`)이 링크를 열어 요약과 대조하고, 범위·중복·중립·현안 누락·검색어 보안을 봅니다.
5. 통과한 브리핑을 대화에 보여 주고 파일 경로(`상황실/브리핑/YYYYMMDD_HHMM_뉴스_브리핑.md`)를 알립니다.
6. **[사람 확인] 건 영향**(있을 때만): `[건 영향]` 줄마다 고릅니다 — 통합일정표에 `제안` 줄 넣기 / 담당 팀장 부르기 / 넘어가기.

- 뉴스 브리핑 형식은 `자료실/서식/뉴스브리핑.md`에 있습니다. 휴대폰에서 읽도록 본문에 표를 쓰지 않습니다.
- `미확인`은 보도는 있으나 당국·당사자가 확인하지 않은 내용, `[확인 필요: 사유]`는 작성자가 원문으로 대조하지 못한 내용입니다.
- 현안 섹션, 한눈에의 `[건 영향]` 줄, 검색 기록은 내부용입니다. 뉴스레터처럼 밖으로 나가는 글의 재료로 쓰지 않습니다.
- 작업 파일은 모두 `상황실/브리핑/`에 날짜·시각 이름으로 쌓이고 동기화되지 않습니다. 보완본은 이름 끝에 `_v2`·`_v3`가 붙습니다.
- 매일 정한 시각에 클라우드에서 자동으로 돌리려면 [아침 뉴스 예약](#아침-뉴스-예약)을 봅니다(처음에는 꺼져 있음).

## 건 폴더와 파일

### 이름
건 폴더 이름은 운영 설정의 '건 폴더 이름'을 따릅니다. 날짜는 접수일이고, 의안번호는 있을 때만 붙입니다. 병합 건은 가장 앞선 번호에 `외N`을 붙입니다.

| 팀 | 폴더 이름의 팀 칸 | 예 (가상) |

| 법제팀 | `법제` | `산출물/20261105_법제_○○법/` |
| 법안검토팀 | `법안검토` | `산출물/20261026_법안검토_○○법_XXXXXXX/`, 병합 건 `…_XXXXXXX외1/` |
| 예결산팀 | `예결산` | `산출물/20261104_예결산_2027예산안/` |
| 조사팀 (단독 건) | `조사` | `산출물/20261105_조사_○○제도입법례/` |
| 심사지원팀 | `심사지원_자료요구`, `심사지원_소위` | `산출물/20261105_심사지원_소위_○○법_XXXXXXX/` |
| 뉴스레터팀 | `뉴스레터` | `산출물/20261201_뉴스레터_12월호/` |

### 안의 파일
| 파일·폴더 | 뜻 |
|---|---|
| `_진행.md` | 단계·사람 결정·검증 회차·승인 기록. 익명 ID도 여기에만 있습니다. 이어서 할 때 먼저 읽습니다 |
| `원자료/` | 안내실에서 옮겨 온 입력 파일과 그 `.md` 사본. 원본은 고치지 않습니다 |
| `원장/` | 법령 MCP 응답 원문. 조문 대조의 기준입니다 |
| `00_위임지시.md` | 팀장이 실무에게 준 지시문. '사람이 정한 것'에 사람의 결정이 들어갑니다 |
| `01_초안.md` | 실무 산출물. 보완하면 `01_초안_v2.md`, `_v3`로 새로 저장하고 맨 위에 보완 내역 표를 답니다 |
| `01c_조문대조.md` | 조문 대조 검사기 결과(대비표를 만드는 팀). 회차마다 아래에 이어 붙입니다 |
| `02_검증보고.md` | 검증 판정문. 회차별로 아래에 쌓입니다 |
| `03_검수포인트.md` | 사람이 먼저 볼 곳. 맨 끝에 AI 작성 고지 한 줄 |
| `04_최종_*` | 사람이 승인한 것만 |
| `조사/` | 이 건 안에서 부른 선행 조사 |
| `_workspace/` | 검토보고서 플러그인 작업 폴더(법안검토팀만) |

- 입력이 `.hwp`·`.hwpx`·`.pdf`면 원본은 그대로 두고 kordoc으로 같은 이름의 `.md` 사본을 만듭니다. kordoc이 없으면 PDF는 `pdf` 스킬로 읽고, HWP는 PDF로 저장해 넣어 달라고 요청합니다.
- `[확인 필요: 사유]`는 원문으로 확인하지 못한 곳, `[판단 필요: 선택지]`는 사람이 정할 곳입니다. 둘 다 검수 때 먼저 봅니다.

## 대시보드
진행 중인 건, 마감, 일정, 현안, 오류노트·교본 현황을 브라우저 한 화면에 모아 보는 진행 현황판입니다. 인터넷 연결이나 외부 자원(CDN·웹 글꼴) 없이 열리는 파일 하나이고, 내용은 생성기가 만든 데이터 파일에서 읽습니다. 화면은 에이전트 기록을 모아 보여 줄 뿐이며, 원문 대조와 최종 판단은 최종 검수자가 합니다.

### 구성
| 파일 | 무엇 | 동기화 |
|---|---|---|
| `도구/대시보드갱신.py` | 생성기. Python 3.8 이상, 표준 라이브러리만 씁니다 | 됨 |
| `상황실/대시보드.html` | 보기 화면. 브라우저에서 더블클릭으로 엽니다 | 됨 |
| `상황실/대시보드_데이터.js`(있으면) | 생성기가 만드는 데이터. 첫 줄 표지(`// Generated dashboard data.`) 뒤에 `window.DASHBOARD_DATA = {...};`가 있고, 건 내용이 들어 있습니다 | **안 됨** (`.gitignore`, 쓰는 중의 임시 파일 포함) |

### 갱신하고 열기
대시보드는 생성기를 돌린 그 순간의 기록을 보여 줍니다. 건이 진행되면 다시 갱신합니다.

1. 프로젝트 폴더(저장소 맨 위)에서 생성기를 돌립니다.
   ```bash
   python3 도구/대시보드갱신.py
   ```
   Windows에서는 이렇게 씁니다.
   ```bat
   py -3 도구\대시보드갱신.py
   ```
2. 생성기가 짧은 요약을 출력합니다: 건 수(진행 중·사람 확인 대기·종결), 7일 안 마감, 지난 마감, 일정 수, 이번 달 오류노트, 경고(읽지 못한 파일 등).
   ```text
   대시보드 데이터를 만들었습니다.
   기준일 2026. 11. 5.(목) · 데이터 파일 …/대시보드_데이터.js
   - 건 3개: 진행 중 1 · 사람 확인 대기 1 · 종결 1
   - 7일 안 마감 1건 · 지난 마감 0건 (열린 건 기준)
   - 일정: 지난 미완료 0 · 오늘부터 14일 2 · 그 뒤 1 (완료·취소 1)
   - 이번 달 오류노트 2줄
   - 경고 0건
   보기: 상황실/대시보드.html 을 브라우저로 엽니다(이미 열려 있으면 새로 고침).
   이 데이터 파일은 건 내용을 담으므로 동기화하거나 게시하지 않습니다.
   ```
   - 열린 건인데 열린 마감이 없는 건이 있으면 마감 줄의 '지난 마감' 뒤에 `· 열린 마감 없음 N건`이, 날짜를 읽지 못한 일정이 있으면 일정 줄 괄호 안에 `날짜 오류 N`이 붙습니다.
   - 경고가 있으면 `경고 N건:` 아래에 `[경고] 파일: 내용` 줄이 이어집니다.
3. `상황실/대시보드.html`을 더블클릭해 브라우저로 엽니다. 이미 열어 두었으면 브라우저에서 새로 고칩니다.

Claude에게 "대시보드 갱신해 줘"라고 해도 됩니다. Claude가 생성기를 돌리고 요약과 HTML 경로만 알려 줍니다. 대시보드는 건 내용을 담으므로 아티팩트·문서·공유 링크로 게시하지 않습니다.

| 옵션 | 뜻 |
|---|---|
| `--today YYYY-MM-DD` | 기준 날짜. 빼면 한국 시각(Asia/Seoul) 오늘입니다. D-n, 지난 마감, '이번 달' 오류노트를 이 날짜로 셉니다. 기준일이 오늘과 다르면 화면 위에 그 날짜 기준이라는 안내가 뜹니다 |
| `--root PATH` | 저장소 폴더. 빼면 `도구/` 바로 위 폴더입니다. `CLAUDE.md`와 `.claude/`가 없는 폴더를 주면 "저장소 폴더가 아닙니다"를 알리고 데이터 파일을 쓰지 않습니다 |
| `--out PATH` | 데이터 파일을 쓸 곳. 빼면 `<root>/상황실/대시보드_데이터.js`입니다. 파일 이름은 `대시보드_데이터.js` 그대로여야 하고, 저장소 안에서는 이 기본 경로에만 씁니다(다른 곳에 쓰면 건 내용이 동기화될 수 있어서입니다). 이미 있는 파일은 이 도구가 만든 데이터 파일(첫 줄 표지)일 때만 덮어씁니다. 보기 화면은 같은 폴더의 이 이름만 읽으므로, 저장소 밖에 쓰면 그 폴더에 `대시보드.html`을 함께 두어야 보입니다 |
| `--selftest` | 가상의 임시 저장소를 만들어 자체 점검하고 통과·실패를 출력합니다. 실제 파일은 건드리지 않습니다 |

- 읽을 파일이 없거나 읽지 못하면 멈추지 않고 경고로 알립니다. 경고가 있어도 데이터 파일은 만듭니다.
- 종료코드: 0 = 데이터 파일을 만듦(`--selftest`는 통과), 1 = 자체 점검 실패, 2 = 데이터 파일을 쓰지 않음(옵션이 틀림, `--root`·`--out`을 받아들이지 않음, 쓰기 실패, 도구 오류, Python 3.8 미만). 종료코드 2일 때 이미 있던 데이터 파일은 바뀌지 않습니다.

### 상태와 마감을 정하는 법
대시보드는 `_진행.md`를 `자료실/서식/진행기록.md` 형식대로 읽습니다. 형식이 어긋나면 상태나 마감이 비어 보일 수 있습니다.

- **상태**: '다음 할 일'이 `없음(종결)`으로 시작하면 종결, `[사람 확인]`으로 시작하면 사람 확인 대기, 그 밖은 진행 중입니다. 사람이 중단한 건도 `없음(종결)`이라 종결로 보입니다.
- **마감**: '마감' 칸에 적힌 일정 ID(`S-YYYYMMDD-XXXX`)를 통합일정표에서 찾아, 상태가 `완료`·`취소`가 아닌 줄 가운데 가장 이른 날짜를 씁니다.
- **대체 줄 따라가기**: 찾은 줄이 `취소`이고 다른 줄의 역산 기준에 `S-… 대체`로 그 ID가 적혀 있으면, 새 줄을 따라갑니다(여러 번 대체돼도 끝까지). 따라간 경로는 건 폴더를 눌러 여는 자세히 보기의 마감 칸에 나옵니다.
- **열린 마감 없음**: 열린 건(진행 중·사람 확인 대기)인데 마감 칸의 일정이 모두 취소·완료됐거나 날짜를 읽지 못하면 마감 칸에 '열린 마감 없음'을 표시하고 경고합니다. 마감 칸의 일정 ID가 통합일정표에 없을 때도 경고합니다. 다음 마감 줄을 통합일정표에 넣고 마감 칸에 그 일정 ID를 더합니다.
- 7일 안 마감과 지난 마감은 열린 건만 셉니다. D-n은 기준일부터 남은 날수(주말 포함)이며, 통합일정표 역산 기준 칸의 D-n(작업일로 거꾸로 센 값)과 다릅니다.
- `_진행.md`가 없는 건 폴더도 '기록 없음' 상태로 목록에 나오고 경고가 붙습니다.
- '마감' 칸에 날짜만 있고 일정 ID가 없으면 마감으로 읽지 않고 경고합니다. 날짜는 통합일정표에 두고 `_진행.md`에는 일정 ID를 적습니다.

### 데이터 보호
- 데이터 파일에는 건 이름·단계·다음 할 일 같은 건 내용이 들어 있습니다. 그래서 동기화하지 않고(`.gitignore`), 그 PC에만 남습니다. 생성기도 저장소 안에서는 `.gitignore`가 빼는 기본 경로에만 씁니다.
- 대시보드 화면이나 데이터 파일을 아티팩트·문서·메일·메신저로 올리거나 공유하지 않습니다. 건 내용이 보이는 화면 캡처도 같습니다.
- 건 폴더가 동기화되지 않으므로, 대시보드에는 **그 PC에 있는 건만** 보입니다.

### 대시보드 문제 해결
| 증상 | 확인할 것 |
|---|---|
| "아직 대시보드 데이터가 없습니다"가 나오거나 화면이 비어 있음 | 데이터 파일이 아직 없습니다. 생성기를 돌린 뒤 화면의 '다시 읽기'를 누르거나 새로 고칩니다(F5, macOS는 ⌘R). `--out`으로 저장소 밖에 썼으면 옵션 없이 다시 돌립니다. 그래도 비면 다른 브라우저로 열어 봅니다 |
| "데이터 형식이 이 화면과 맞지 않습니다" | 생성기(`도구/대시보드갱신.py`)와 화면(`상황실/대시보드.html`)의 판이 다르거나 데이터 파일이 중간에 끊겼습니다. 두 파일을 같은 판으로 맞추고(동기화했으면 둘이 함께 바뀌었는지 봅니다) 생성기를 다시 돌린 뒤 새로 고칩니다 |
| 내용이 예전 그대로임 | 생성기를 다시 돌리고 새로 고칩니다. 화면은 마지막 생성 시각의 기록입니다(맨 아래 생성 시각 확인) |
| 있어야 할 건이 안 보임 | '종결 숨기기'와 팀·상태·마감 필터를 봅니다. 다른 PC에서 진행한 건은 이 PC에 건 폴더가 없으면 나오지 않습니다 |
| 마감이 비어 있거나 '열린 마감 없음'이 나옴 | `_진행.md` '마감' 칸에 날짜가 아니라 일정 ID가 있는지, 그 ID의 줄이 통합일정표에 있는지 봅니다. 날짜를 바꿨으면 새 줄의 역산 기준에 `S-… 대체`가 있는지, 대체 줄이 승인됐을 때 '마감' 칸에 새 일정 ID가 더해졌는지 봅니다. 마감 일정이 모두 끝났는데 건이 열려 있으면 다음 마감 줄을 넣어 달라고 팀장에게 요청합니다 |
| 일정이 표에 있는데 화면에 없음 | 표 중간에 빈 줄처럼 `\|`로 시작하지 않는 줄이 있으면 그 뒤 줄은 읽지 않습니다(점검 도구도 같습니다). 요약의 일정 수가 적거나 "마감의 일정 ID …가 통합일정표에 없습니다" 경고로 드러납니다. 그 줄을 지웁니다 |
| 날짜나 D-n이 이상함 | 기준 날짜는 한국 시각 오늘입니다(요약 첫 줄의 '기준일'). 다른 날 기준으로 보려면 `--today`를 씁니다. 통합일정표 날짜는 `2026. 11. 5.(목)` 형식이어야 합니다. 요일이 날짜와 다르거나 날짜를 읽지 못한 줄은 상태와 관계없이 생성기 경고로 나오고, 날짜를 읽지 못한 줄은 일정 탭 맨 아래에도 모입니다. `python3 도구/일정내보내기.py 점검`은 `확정`·`완료` 줄만 날짜를 검사합니다 |
| 요약에 경고가 있음 | 경고 줄에 읽지 못한 파일이 나옵니다. `_진행.md`가 없는 건 폴더, 표 형식이 깨진 파일 등을 고칩니다 |
| "날짜 형식이 아닙니다"(종료코드 2) | `--today` 값을 `YYYY-MM-DD`(예: 2026-11-05)로 다시 씁니다 |
| "저장소 폴더가 아닙니다"(종료코드 2) | `--root`에 `CLAUDE.md`와 `.claude/`가 있는 폴더를 주거나, `--root`를 빼고 돌립니다 |
| "데이터 파일을 쓰지 않았습니다"(종료코드 2) | `--out`의 이름이 `대시보드_데이터.js`가 아니거나, 저장소 안의 기본 경로가 아니거나, 이미 있는 파일이 이 도구가 만든 데이터 파일이 아닙니다. 아래 줄에 까닭이 나옵니다. 보통은 `--out`을 빼고 돌립니다 |
| "데이터 파일을 쓰지 못했습니다"(종료코드 2) | 상황실 폴더(또는 `--out` 폴더)에 쓸 권한과 남은 공간이 있는지 봅니다 |
| "Python 3.8 이상이 필요합니다"(종료코드 2) | Python을 새 판으로 설치합니다(`python3 --version`으로 확인) |
| "데이터를 만들지 못했습니다(도구 오류: …)"(종료코드 2) | 생성기의 결함입니다. 데이터 파일은 바뀌지 않았습니다. 출력 전체를 Claude에게 보여 주고, `--selftest`로 자체 점검을 돌려 봅니다 |

## 일정과 캘린더
모든 팀의 마감·회의는 `상황실/통합일정표.md` 한 표에 모입니다. 기입 규칙과 캘린더 일정 형식은 그 파일 머리에만 있습니다.

### 일정 상태
| 상태 | 뜻 | 누가 |
|---|---|---|
| `제안` | 팀이나 상황실 실무가 넣은 줄 | 각 팀장, 상황실 실무 |
| `확정` | 사람이 승인한 줄. Google Calendar에는 이 줄만 들어갑니다 | 상황실이 사람 승인을 받아 바꿈 |
| `완료` | 끝난 일 | 상황실 |
| `취소` | 없어진 일. 캘린더에 있었으면 지웁니다 | 상황실 |

- `확정` 줄은 상황실만 고칩니다. 날짜를 바꾸려면 팀이 새 `제안` 줄을 넣고 역산 기준에 `S-… 대체`를 적습니다. 승인되면 상황실이 옛 줄은 `취소`, 새 줄은 `확정`으로 바꾸고, 옛 일정 ID를 마감 칸에 적은 건의 `_진행.md`에 새 일정 ID를 더합니다. 대시보드도 `S-… 대체`를 따라 바뀐 마감을 찾고, 열린 건에 열린 마감이 없으면 경고합니다.
- 일정 ID는 `S-YYYYMMDD-XXXX`(넣은 날과 무작위 4자리)입니다. 처음 정한 뒤 바꾸지 않고 .ics 파일의 UID로도 씁니다.
- 건 칸은 `접수일_제명(개정범위)_이름`입니다. 예: `20261105_○○법(일부)_홍길동`. 법제팀 건(발의 전 의뢰)은 이름을 성만 남기고 `**`로 가립니다. 예: `20261105_○○법(일부)_홍**`.
- 이름이 들어가는 이 형식은 배포본의 기본 형식입니다. 기관 보안 지침에 맞지 않으면 조직 변경으로 바꿉니다(예: 이름 빼기, [처음 채울 것](#처음-채울-것)).
- 마감은 `자료실/규칙/마감역산.md`대로 기준 기한 → 사람 승인 → 검증 통과 → 초안 순으로 거꾸로 셉니다. 역산 일수는 토·일·공휴일을 뺀 작업일 기준입니다.

| 방법 | 언제 | 어떻게 |
|---|---|---|
| 커넥터 | Google Calendar 커넥터를 연결한 PC·세션 | 상황실 팀장이 사람 승인을 받아 넣을 캘린더에 만들기·고치기·지우기를 합니다 |
| .ics 파일 | 커넥터가 없을 때 | `발송실/`에 .ics를 만들어 드리면 Google Calendar 설정 → 가져오기로 넣습니다. 가져온 뒤 "가져왔어"라고 알려 주면 캘린더 칸을 고칩니다 |

```bash
python3 도구/일정내보내기.py 점검
python3 도구/일정내보내기.py ics 발송실/통합일정표_YYYYMMDD_HHMM.ics
```

- 점검은 보낼 줄·바뀐 줄·지울 줄·읽지 못한 줄을 알려 주고, 표는 고치지 않습니다. 날짜·시각·요일은 캘린더로 갈 `확정`·`완료` 줄만 검사합니다. `ics`에 `--all`을 붙이면 `확정` 줄을 모두 내보냅니다(새 캘린더용).
- .ics 가져오기는 이미 있는 일정을 고치거나 지우지 못할 수 있습니다. 그래서 바뀐 줄·지울 줄은 브리핑에 적어 드리고, 사람이 캘린더에서 직접 고칩니다.
- 캘린더 일정의 제목은 `<건> · <일>`, 본문은 `통합일정표에서 옮김 · 일정 ID S-…` 한 줄입니다. 검토 내용·의견·첨부, 참석자 초대, 알림 메일은 넣지 않습니다.
- 캘린더에서 일정을 직접 바꾸면 다음 브리핑에 '캘린더에서 바뀜'으로 나옵니다. 표를 캘린더에 맞출지, 캘린더를 표대로 되돌릴지 사람이 정하기 전에는 어느 쪽도 덮어쓰지 않습니다.

## 아침 뉴스 예약
상황실 뉴스 모드를 매일 정한 시각에 클라우드에서 자동으로 돌리는 선택 기능입니다. **배포본에서는 꺼져 있습니다.** 상황실 팀 설정의 '뉴스 예약 실행' 칸이 `없음`이면 예약이 없는 상태입니다. 예약하지 않아도 `/ops-desk 뉴스`로 언제든 직접 돌릴 수 있습니다.

### 작동 방식
claude.ai 예약작업 「오늘의 뉴스」가 정한 시각에, 같은 이름의 전용 클라우드 세션 「오늘의 뉴스」에 실행 메시지를 넣습니다. 그 세션이 저장소를 main 최신으로 맞춘 뒤 상황실 뉴스 모드를 무인으로 돌립니다. 브리핑은 그 세션 대화에 날짜별로 쌓이고, 휴대폰 알림에는 첫 줄 `# M월 D일 뉴스`가 보입니다.

### 켜는 법
1. 미리 확인: 내 비공개 저장소의 main에 최신 내용이 올라가 있고, claude.ai/code에서 이 저장소를 고를 수 있어야 합니다. 국가법령정보 MCP를 claude.ai 커넥터로 연결해 두었으면([국가법령정보 MCP 연결](#국가법령정보-mcp-연결)) 법령 확인까지 하고, 없으면 `[확인 필요: 법령 MCP 미연결]`로 남깁니다.
2. 전용 세션 만들기: claude.ai/code에서 이 저장소를 골라 새 클라우드 세션을 만들고, 세션 제목을 「오늘의 뉴스」로 정합니다.
3. 실행 메시지 찾기: `.claude/skills/ops-desk/SKILL.md`의 '절차 — 뉴스' 아래 '무인 실행' 절 끝 코드 블록이 실행 메시지입니다. `[오늘의 뉴스 예약 실행]`으로 시작하며, 글을 고치지 않고 그대로 씁니다.
4. 예약작업 만들기: claude.ai에서 「오늘의 뉴스」라는 예약작업을 만들어, 정한 시각(한국 시각)에 2의 세션으로 3의 실행 메시지를 보내게 합니다. 예약작업을 다룰 수 있는 Claude 세션에 "세션 「오늘의 뉴스」에 매일 아침 이 실행 메시지를 보내는 예약작업을 만들어 줘"처럼 요청해도 됩니다.
5. 팀 설정에 적기: "상황실 팀 설정의 뉴스 예약 실행을 매일 07:40(한국 시각)으로 적어 줘"처럼 요청합니다. 조직 변경 절차대로 고치고 구성점검·변경이력·동기화를 거칩니다.
6. 다음 날 아침 세션 대화에 브리핑이 쌓였는지 확인합니다.

### 무인 실행이 하는 것과 하지 않는 것
물을 수 없는 실행이라 상황실 스킬의 '무인 실행' 규칙을 따릅니다.

- 같은 날 브리핑이 있으면 '그 뒤 소식만'으로 만듭니다.
- `상황실/현안목록.md`·`상황실/통합일정표.md`·`라운지/오류노트.md`를 고치지 않습니다. 지울 종료 줄, 목록에 없는 건, `[건 영향]`은 브리핑 현안 섹션에 적기만 합니다.
- 커밋·푸시·PR·게시, 메일 발송, 캘린더 쓰기를 하지 않습니다.
- 마지막 응답은 검증을 통과한 브리핑 본문입니다(출처 목록·검색 기록 제외). 검증을 통과하지 못했으면 `[검증 미통과]` 표시와 남은 지적사항이 붙습니다.

### 한계
- 그 세션은 뉴스 전용입니다. 다른 일을 시키지 않습니다(대화가 길어지면 앞 내용이 요약됩니다).
- 컨테이너가 바뀌면 브리핑 파일은 남지 않습니다. 대신 대화에 남은 전날 브리핑으로 중복을 대조합니다.
- 현안은 main의 `상황실/현안목록.md`로 조사합니다. PC에서 등록한 건은 동기화해 main에 들어가야 다음 아침부터 반영됩니다.
- 현안목록의 줄 정리(기간이 지난 종료 줄)와 목록에 없는 건 등록은 예약 실행에서 하지 않습니다. PC에서 `/ops-desk 뉴스`를 돌릴 때 합니다.
- `[건 영향]`도 예약 실행에서는 처리하지 않으므로, 브리핑을 보고 필요하면 PC에서 담당 팀장을 부르거나 일정을 넣습니다.
- 클라우드 환경의 네트워크 설정에 따라 국회 의안정보시스템(likms.assembly.go.kr)·국회 입법예고(pal.assembly.go.kr) 같은 사이트가 막힐 수 있습니다. 막혀 있으면 의안 확인이 `[확인 필요]`로 남습니다([문제 해결](#문제-해결-faq)).
- 브리핑의 현안 섹션은 공개 키워드로만 만들지만 내부용입니다. 세션 대화를 공유 링크로 내보내지 않습니다.

## 상급자 피드백
상급자에게 받은 피드백은 **이번 건 보완**과 **검증 기준 갱신**에 함께 씁니다. 절차의 원본은 `CLAUDE.md`의 '상급자 피드백'입니다.

1. **올리기**: 메모·메일·의견이 달린 HWP·PDF를 `안내실/피드백/`에 넣거나 채팅에 붙여 넣고 "상급자 피드백 반영해 줘"라고 요청합니다. 어느 건인지 함께 알려 주면 좋습니다.
2. **항목 확인**: 팀장이 그 건의 `원자료/`에 원문 사본(`상급자피드백_YYYYMMDD.md`)과 항목 파일(`상급자피드백_YYYYMMDD_항목.md`)을 만듭니다. PDF·HWP의 주석·메모도 뽑아 사본 끝 '주석' 절에 넣습니다.
3. **[사람 확인] F 목록**: F1, F2…로 나눈 목록 전체를 보고 빠진 항목이 없는지 확인합니다. 항목마다 반영·제외를 정하고, 뜻이 모호하거나 앞선 결정과 부딪치는 항목에 답합니다.
4. **이미 끝난 건이면 [사람 확인]**: 다시 열어 고친다 / 이번 건은 그대로 두고 검증 기준만 갱신한다. 다시 열면 승인을 다시 받아 `04_최종_*`를 `_v2`로 새로 저장하고 출력 파일도 다시 만듭니다.
5. **이번 건 반영**: '반영' 항목이 실무에게 보완 지시로 돌아갑니다(대비표 팀은 조문 대조도 다시). 이후 모든 검증 회차가 항목마다 반영 여부를 확인하고, 통과하면 그 팀의 확정·승인 관문으로 돌아갑니다. `03_검수포인트.md`에는 피드백을 반영한 곳이 '피드백 반영' 소절로 더해집니다. 이 소절은 검수포인트 개수에 세지 않고, AI 작성 고지 줄은 그대로 맨 끝에 둡니다.
6. **검증 기준 반영**: 항목마다 오류노트에 '발견자: 상급자'로 한 줄씩 적고, `/coaching 피드백`으로 체크리스트 갱신안을 만듭니다. 사람이 채택한 항목만 체크리스트에 들어갑니다.

- 사람·상급자 요구로 되돌린 것은 보완 한도에 세지 않습니다.
- **특정 건이 아닌 일반 지침**이면 원본을 `안내실/피드백/처리함/YYYYMMDD/`로 옮기고 같은 곳에 사본과 항목 파일을 만듭니다(동기화되지 않음). F 목록 확인과 함께 적용할 유형(체크리스트)도 정합니다. 절차나 통과 조건을 바꿀 내용이면 `라운지/개선안.md`에도 적힙니다.
- 피드백 원본과 사본은 건 폴더나 `안내실/`에만 둡니다. 동기화되는 파일에는 이름·법률명·원문 인용 없이 일반화한 내용만 적힙니다.
- 상황실 오늘 브리핑에서 결과물에 대한 상급자 의견 메일이 보이면, 이 절차로 넘길지 묻습니다.

## 교본과 훈련
사람이 놓친 것, 검증이 놓친 것을 다음 건의 검증 기준으로 바꾸는 순환입니다.

```text
건 종료 → 오류노트(익명) → /coaching 교본갱신 → 사람이 채택 → 검수 체크리스트 → 다음 건의 검증 입력
```

### 오류노트
건이 끝나면 팀장이 `라운지/오류노트.md`에 한 줄씩 적습니다. 검증이 찾은 오류, 사람이 추가로 찾은 오류, 검증이 잘못 짚은 지적(오탐)을 모두 적습니다.

| 칸 | 적는 것 |
|---|---|
| 건 | 익명 ID `건-XXXXXX`만. 건 폴더가 없는 일은 `-` |
| 유형 | 유형 코드(인용·수치·누락·체계·최신·형식·논리·판단·중립·보안) |
| 발견자 | 검증 / 사람 / 상급자 / 오탐 |
| 내용 | "개정문 지시문의 항 번호가 현행과 다름"처럼 일반화한 한 줄 |
| 다음에 볼 곳 | 규칙·서식·체크리스트 경로나 절차 단계. 검증이 통과시킨 것을 사람·상급자가 찾았으면 `검증 놓침` |

오류노트는 GitHub로 동기화되므로 법률명·의안번호·의원·기관·상급자 이름, 건 폴더 이름, 피드백·의뢰 원문 인용을 적지 않습니다. 익명 ID와 건의 대응은 동기화되지 않는 `_진행.md`에만 있습니다.

### 교본갱신
- 운영 설정의 교본갱신 주기마다 `/coaching 교본갱신`을 돌립니다. 최근 7일 오류노트를 유형별로 묶어 체크리스트 추가·수정·폐지안을 만들고, '발견자: 상급자'와 `검증 놓침` 줄을 먼저 다룹니다.
- 갱신안은 `라운지/훈련/YYYYMMDD_HHMM_<유형>_교본갱신안.md`에 생깁니다. **[사람 확인]** 항목마다 채택·기각과 중대도를 정합니다.
- 채택한 항목만 `자료실/교본/검수체크리스트_<유형>.md`에 들어갑니다. 체크리스트는 사람이 직접 고치지 않고 이 경로로만 갱신합니다. 빼는 항목은 지우지 않고 상태를 `폐지`로 바꿉니다.
- 체크리스트가 생기면 그 유형의 검증마다 `사용` 항목을 하나씩 점검해 판정문의 '체크리스트 점검'에 적습니다.
- 주기대로 자동으로 돌리려면 `/loop` 또는 예약 작업으로 `/coaching 교본갱신`을 겁니다.

### 훈련과 채점
- 운영 설정의 훈련 주기마다 `/coaching 훈련 <유형>`을 합니다. 승인된 과거 결과물(`04_최종_*`), 없으면 선례에 오류 3~5개를 심은 문제 파일이 `라운지/훈련/`에 생깁니다. 둘 다 없으면 만들지 않고 선례 넣는 법을 알려 줍니다.
- 문제 파일만 열어 오류를 찾고 답을 냅니다. 정답 파일은 채점 전에 열지 않습니다.
- `/coaching 채점`으로 찾은 것·놓친 것·오답과, 놓친 유형마다 체크 요령을 받습니다. 결과는 `라운지/훈련기록.md`에 한 줄(날짜·유형·심은 오류 수·찾은 수·놓친 유형·소요 시간)로 남습니다.
- 훈련 문제·정답은 승인된 건 결과물로 만들기 때문에 동기화되지 않고, 만든 PC에만 있습니다.

## 설정 바꾸기와 팀 추가
업무기술서와 규칙은 일하면서 계속 고쳐 쓰는 문서입니다. 무엇을 어디서 고치는지는 `수정안내.md`에 표로 있습니다.

### 바꾸는 순서
가장 쉬운 방법은 평소 말로 요청하는 것입니다. 예: "운영 설정에서 보완 한도를 3회로 바꿔 줘", "뉴스레터 꼭지 분량을 400~600자로 바꿔 줘", "뉴스 심층 관심사를 기후·에너지로 정해 줘".

1. Claude가 `수정안내.md`에서 고칠 곳을 찾습니다. 같은 값은 한 곳만 고칩니다.
2. 무엇을 어떻게 바꿀지 한두 줄로 보여 주고 확인을 받습니다. 오탈자·표기만 고칠 때는 바로 고칩니다.
3. 고친 뒤 `python3 도구/구성점검.py`(Windows는 `py -3 도구\구성점검.py`)로 오류가 0건인지 확인합니다.
4. `변경이력.md`에 한 줄 적습니다.
5. 동기화할지 묻습니다. 올릴 파일 목록을 먼저 보여 주고, 승인하면 동기화합니다.

| 바꾸고 싶은 것 | 고칠 곳 |
|---|---|
| 여러 팀이 쓰는 값(보완 한도, 검수포인트 개수, 주기 등) | `CLAUDE.md` 운영 설정. 법안검토팀 플러그인 경로의 되돌림 횟수는 플러그인이 정하므로 여기서 바뀌지 않습니다 |
| 통합일정표 건 표시(이름을 넣을지 등) | `상황실/통합일정표.md` 머리의 기입 규칙 |
| 한 팀의 분량·후보 수·선정 기준·산출물 | 그 팀장 스킬의 팀 설정 |
| 팀의 진행 순서, 사람에게 묻는 시점 | 그 팀장 스킬의 절차 |
| 실무가 하는 일, 검증 통과 조건 | `.claude/agents/<팀ID>-writer.md`, `.claude/agents/<팀ID>-checker.md` |
| 법정 기한·역산 일수·공휴일 | `자료실/규칙/마감역산.md` |
| 우리 기관 형식 | 파일을 고치지 말고 `자료실/선례/<유형>/`에 선례를 넣습니다 |
| 검수 체크리스트 항목 | 직접 고치지 않고 `/coaching 교본갱신`·`/coaching 피드백`으로 |

예전 내용으로 되돌리고 싶으면 "○○ 파일을 지난주 내용으로 되돌려 줘"라고 요청합니다. 모든 수정이 git 기록에 남아 있습니다.

### 팀 추가
1. 팀 ID(영문 소문자·숫자·하이픈)와 한글 이름을 정합니다. 팀 ID가 곧 호출 명령입니다.
2. `도구/새팀_템플릿/`의 세 파일을 팀장 스킬·실무·검증 자리로 복사하고 `{{ }}` 자리를 모두 채웁니다.
3. 선례 폴더를 만들고, 역량강화실 팀 설정의 '팀 → 유형'에 넣습니다.
4. 대비표를 만드는 팀이면 조문 대조 설정을 더합니다. 현안 등록 대상 팀에 넣을지도 정합니다.
5. `CLAUDE.md` 건물 배치와 `README.md` 구성 표에 넣고, 구성점검 → 변경이력 → 동기화를 거칩니다.

자세한 단계와 팀 이름 바꾸기·없애기는 `수정안내.md`의 '팀 추가'와 '팀 이름 바꾸기·없애기'에 있습니다. "○○ 지원팀을 새로 만들어 줘"처럼 요청하면 Claude가 그 순서대로 합니다.

## 동기화와 클라우드 세션

### 매일 동기화
| OS | 실행 |
|---|---|
| Windows | `동기화.cmd` 더블클릭 |
| macOS·Linux | `./동기화.sh` |

- 작업 시작 전과 끝난 뒤 한 번씩 실행합니다. 올릴 변경 목록을 먼저 보여 주고, `y`를 눌러야 올립니다.
- 순서는 내 변경 커밋 → 다른 PC 변경 받기 → 충돌 표지(`<<<<<<<`) 검사 → 올리기입니다. 충돌이 나면 아무것도 올리지 않고 멈추며, 내 변경은 그 PC에 커밋으로 남습니다.
- Claude가 대신 돌릴 때는 올릴 파일 목록을 먼저 보여 주고 승인을 받은 뒤, OS와 관계없이 `./동기화.sh --yes`로 돌립니다(Windows는 Git Bash).
- 두 스크립트는 스크립트가 있는 폴더가 git 저장소의 맨 위일 때만 돕니다. 배포 저장소 안의 `vanilla` 폴더나 git 저장소가 아닌 폴더에서 돌리면 아무것도 올리거나 받지 않고 멈춥니다. 이때는 폴더를 밖으로 복사해 자기 저장소로 만든 뒤([내 비공개 저장소 만들기](#내-비공개-저장소-만들기)) 그 폴더에서 다시 돌립니다.
- 동기화가 멈추면 Claude에게 "동기화 충돌 해결해 줘"라고 요청합니다.

### 여러 PC에서 쓸 때
- 오류노트·훈련기록·변경이력처럼 줄을 더하기만 하는 표는 두 PC가 동시에 줄을 더해도 자동으로 합쳐집니다(`.gitattributes`).
- 이 표들의 머리(적는 법)나 이미 있는 줄을 고치거나 지울 때는 고치기 전과 후에 바로 동기화합니다. 그 밖의 파일은 두 PC에서 동시에 고치지 않습니다.
- 업무기술서·규칙을 고치기 전에는 동기화부터 합니다.
- 설치키트, `.env`, 문서 스킬, 커넥터는 PC마다 따로 확인합니다([준비와 설치](#준비와-설치)).

### 클라우드 세션 (claude.ai/code)
내 저장소를 골라 세션을 시작하면 브라우저·모바일에서도 같은 팀을 씁니다.

- 세션 컨테이너는 끝나면 지워집니다. 업무기술서·자료실 변경은 커밋·푸시하고, 건 폴더는 동기화 대상이 아니므로 이어 하려면 내려받아 둡니다.
- 클라우드 세션에서 올린 변경은 세션 브랜치(`claude/…`, `ccr-…` 등)에만 들어가고 main에는 들어가지 않습니다. 다른 PC에서 받으려면 GitHub에서 그 브랜치를 main에 병합합니다. PR을 만들거나 병합하는 일은 사람이 하거나, 사람이 요청할 때 Claude가 합니다.
- 다 쓴 세션 브랜치를 지울지는 사람이 정합니다.
- 클라우드 세션에는 kordoc과 검토보고서 플러그인이 없고, `.env`도 없습니다. HWP는 PDF로 넣고, 법안검토는 예비 경로로 할지 PC에서 이어 할지 정합니다.
- 국회 사이트가 막히면 세션 제목 줄의 환경 메뉴 → 편집 → 네트워크 접근에서 허용 도메인에 넣습니다.

## 보안 수칙
- **외부로 내보내지 않는 것**: 의뢰 내용·미공개 자료·의원실 정보는 외부 검색어나 외부 서비스 입력에 넣지 않습니다. 검색은 공개 키워드로만 합니다. 조사팀은 공개 검색어 목록을 먼저 만들고, 뉴스 실무는 현안을 공개 키워드로만 압니다.
- **보내기·게시는 사람이**: 에이전트는 메일 발송, 일정 초대(참석자 추가), 게시를 하지 않습니다. 승인본을 `발송실/`에 놓으면 사람이 직접 보냅니다.
- **게시의 범위**: claude.ai 아티팩트·Claude Docs 문서 만들기, GitHub 이슈·PR·댓글 쓰기, 공유 링크 만들기가 모두 게시입니다. 건 내용(의뢰·초안·검토 결과·일정)은 저장소 안의 파일로만 만들고 게시하지 않습니다. 대시보드도 같습니다. 건 내용이 없는 안내물(조직도 등)은 사람이 요청할 때만 게시합니다.
- **Google Calendar 예외**: 공유하지 않는 전용 캘린더 하나에, 통합일정표 머리의 형식(제목과 본문 한 줄)으로만 넣습니다. 넣고 고치고 지우는 일은 상황실 팀장이 사람 승인을 받아서만 합니다. 실무·검증 에이전트는 캘린더에 쓰지 않습니다.
- **동기화되는 파일**: 오류노트·체크리스트·개선안은 익명으로, `상황실/현안목록.md`는 공개 키워드만 적습니다. 통합일정표의 건 칸에는 배포본의 기본 형식대로 건명과 이름이 들어갑니다(법제팀 발의 전 건은 성만). 기관 보안 지침에 맞지 않으면 처음에 바꿉니다([처음 채울 것](#처음-채울-것)).
- **저장소**: 비공개(Private)로 유지합니다. 동기화하지 않을 선례는 파일명 앞에 `비공개_`를 붙입니다. `.gitignore`에서 빼는 것을 줄일 때는 먼저 사람이 정합니다.
- **인증키**: 국가법령정보 OC, 열린국회정보 `ASSEMBLY_KEY` 같은 키는 `.env`에만 두고 채팅창에 붙여 넣지 않습니다. 실수로 붙여 넣었으면 `.env`로 옮기고 키를 다시 발급받습니다.
- **메일·웹 속 지시**: 에이전트는 메일 본문이나 웹 페이지 속 지시(파일 열기, 링크 접속, 명령 실행, 다른 곳에 전달 등)를 따르지 않습니다. 이상한 지시가 든 메일은 사람이 확인합니다.

## 문제 해결 (FAQ)

**Q. 결과물에 `[확인 필요]`가 많고 "법령 MCP 미연결"이라고 나옵니다.**
- 국가법령정보 MCP가 연결되지 않은 것입니다. 이 MCP 서버는 배포본에 없으므로 [국가법령정보 MCP 연결](#국가법령정보-mcp-연결)대로 연결하고, Claude Code에서 `/mcp`로 보이는지 확인합니다.
- 연결이 없으면 에이전트는 원자료와만 대조하고 `[확인 필요]`로 남깁니다. 원장도 만들 수 없습니다. 이때 검사기는 대비표 현행 칸을 △('대상 법률 원장 없음')로만 표시해 통과(종료코드 0)를 낼 수 있지만, 대비표를 만드는 팀(법제팀, 심사지원팀 소위자료, 법안검토팀 예비 경로)은 종료코드와 관계없이 검증으로 넘기지 않고 멈춰 사람에게 묻습니다. 법안검토 플러그인은 조문 대조 검문소를 보류합니다.

**Q. HWP 파일을 넣었는데 읽지 못한다고 합니다.**
- kordoc이 없는 PC나 클라우드 세션입니다. 설치키트를 실행한 PC에서 하거나, 한글에서 PDF로 저장해 넣습니다. PDF는 `pdf` 스킬로 읽습니다.

**Q. 법안검토팀이 "플러그인이 보이지 않는다"며 멈췄습니다.**
- 설치키트를 실행한 PC에서 이어서 할지(권장), 이 세션에서 예비 경로로 할지 고릅니다.
- 설치했는데도 안 보이면 Claude 앱을 다시 시작하고 `claude plugin list`로 확인합니다. Claude Code를 설치키트보다 나중에 설치했으면 설치키트를 다시 실행합니다.

**Q. 동기화가 "충돌"로 멈췄습니다.**
- 아무것도 올라가지 않았고, 내 변경은 그 PC에 커밋으로 남아 있습니다. Claude에게 "동기화 충돌 해결해 줘"라고 요청합니다.
- 받기(pull)나 올리기(push) 실패는 네트워크·GitHub 로그인·원격 브랜치 문제입니다. 메시지를 Claude에게 보여 줍니다.
- "이 폴더가 git 저장소의 맨 위가 아닙니다"(Windows는 `this folder is not the top of its own git repository`)로 멈추면, 배포 저장소 안의 `vanilla` 폴더처럼 자기 저장소가 아닌 곳에서 돌린 것입니다. 폴더를 밖으로 복사해 자기 저장소로 만든 뒤 다시 돌립니다.

**Q. "보완 한도를 넘었다"며 사람에게 넘어왔습니다.**
- 검증 보완과 조문 대조 불통과로 되돌린 수가 운영 설정의 보완 한도를 넘은 것입니다. 남은 지적사항과 선택지를 보고 방향을 정합니다.
- 법안검토팀 플러그인 경로는 이 한도가 아니라 플러그인의 고정 횟수를 넘으면 '보류'로 멈춥니다. 남은 항목과 필요한 자료를 보고 자료를 보강하거나 범위를 조정해 다시 하게 합니다.
- 반려 기준(방향 자체가 틀림, 원자료 부족, 사람 판단이 필요한 쟁점)에 해당하는지도 함께 봅니다. 사람이 방향을 정해 수정을 요구하면 셈은 0부터 다시 시작합니다.

**Q. 클라우드 세션에서 국회 사이트나 열린국회정보 API가 열리지 않습니다.**
- 클라우드 환경의 네트워크 설정 때문입니다. 세션 제목 줄의 환경 메뉴 → 편집 → 네트워크 접근에서 허용 도메인(예: likms.assembly.go.kr, pal.assembly.go.kr, open.assembly.go.kr)을 넣습니다.
- 막혀 있는 동안 의안 확인은 `[확인 필요]`로 남습니다.

**Q. 국회 API 점검이 실패합니다.**
- `[실패] 접속 불가`: 네트워크 문제입니다. 클라우드 세션이면 위 질문을 봅니다.
- 인증키가 유효하지 않다고 나오면 열린국회정보 누리집에서 키를 확인합니다.
- `.env를 UTF-8로 읽지 못했다`가 나오면 메모장 등에서 인코딩을 UTF-8로 골라 `.env`를 다시 저장합니다.

**Q. 메일이 '사본 없음'이나 '내용 확인 불가'로 나옵니다.**
- Outlook의 .msg 등 읽지 못하는 형식입니다. .eml이나 .txt로 다시 내보내 `안내실/메일/`에 넣습니다. 그대로 진행하면 그 메일은 브리핑에 '내용 확인 불가'로 남습니다.

**Q. 예결산 검증이 「재계산 미실행」 때문에 멈췄습니다.**
- 수식 계산값이 파일에 들어가지 않은 것입니다. `01_표_재계산.xlsx`를 Excel로 한 번 열어 저장한 뒤 알려 줍니다.
- 판정문에 `[확인 필요: openpyxl 없음]`이 있으면 검증이 수식을 읽지 못해 수식 점검을 판정에서 뺀 것입니다. `python3 -m pip install openpyxl`로 설치한 뒤 검증을 다시 요청합니다.

**Q. 조문 대조가 실행 오류(종료코드 2)이거나 '대비표 0개'로 나옵니다.**
- 대비표 머리 칸이 정확히 `현 행` · `개 정 안`인지, 조 제목과 `(생 략)`을 한 칸에 함께 쓰지 않았는지, 원장 머리말(`- 법령:`, `- 기준일:`, `- 조회:`, `---`)이 있는지 봅니다. 표기 규칙은 `자료실/규칙/조문대조.md`에 있습니다.
- 실행 오류 상태로는 검증에 넘기지 않습니다. 고친 뒤 다시 돌립니다.

**Q. 발의서 HWPX나 대비표 DOCX가 만들어지지 않았습니다.**
- 그 PC·세션에 문서 스킬(`bill-hwpx-autofill`, `amendment-comparison-table`, `참고조문`)이나 kordoc이 없는 것입니다. 이때는 마크다운 확정본만 만들고 "도구 미연결로 ○○ 파일 미생성"이라고 알립니다.
- 이 세 스킬은 배포본에 들어 있지 않고 공개된 표준 스킬도 아닙니다. 기관이 따로 마련한 경우에만 계정 스킬로 둡니다.

**Q. Python이 없다고 나옵니다.**
- 구성점검, 메일 사본, 일정 점검·.ics, 조문 대조, 예결산 재계산, 대시보드가 Python 3.8 이상을 씁니다. Python을 설치하거나 새 판으로 올립니다. Windows에서는 `py -3` 또는 `python`으로 부릅니다.
- 판은 `python3 --version`으로 봅니다. 3.8보다 낮으면 대시보드 생성기는 데이터 파일을 쓰지 않고 멈춥니다.

**Q. 같은 이름의 건 폴더가 있다고 묻습니다.**
- 그 `_진행.md`를 보고 같은 건이면 "같은 건"이라고 답해 이어 합니다. 다른 건이면 이름 끝에 `_2`가 붙은 새 폴더가 생깁니다.

**Q. 다른 PC에서 하던 건을 이어 하고 싶습니다.**
- 건 폴더는 동기화되지 않습니다. 하던 PC에서 건 폴더를 통째로 옮긴 뒤 "이어서 해 줘"라고 요청합니다.

**Q. 일정 점검 도구가 `[읽지 못함]`을 냅니다.**
- 칸 수가 표 머리와 다르거나, 일정 ID 형식이 틀렸거나 중복됐거나, 상태·건·캘린더 칸 값이 규칙에 없거나, `확정`·`완료` 줄의 날짜·시각·요일이 맞지 않는 줄입니다. 그 줄을 `상황실/통합일정표.md` 머리의 기입 규칙대로 고칩니다.
- `제안` 줄의 날짜·요일은 이 점검이 보지 않습니다. 대시보드 생성기의 경고로 확인합니다.

**Q. 구성점검에 오류가 나옵니다.**
- 오류 줄에 어느 파일의 어느 경로·명령이 없는지 나옵니다. "구성점검 오류 고쳐 줘"라고 요청하면 Claude가 `수정안내.md`대로 고치고 다시 점검합니다.

**Q. 결과물을 아티팩트나 공유 링크로 보고 싶습니다.**
- 건 내용은 게시하지 않습니다. 결과물은 저장소 안의 파일로 열어 보고, 밖으로 보낼 것은 승인 뒤 `발송실/`에서 사람이 직접 보냅니다.
